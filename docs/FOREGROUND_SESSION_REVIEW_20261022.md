# TunBox 打开应用时的误重连修复

状态：源码已修复并完成自动回归；HarmonyOS SDK 26.0.0.105 调试 HAP 编译通过，真机锁屏与会话持续性验收待完成。

基线：`xiaoli8571/TunBox`，v0.4.3 / `cfcc5c5aa93d45a627ce70abebbab0487b879410`。

## 已证实的问题

1. UI 存活监控每 3 秒检查扩展进程的心跳。原版把超过 15 秒的旧心跳当作一次即可升级的死亡证据，直接进入修复；此前没有确认真实 controller 是否仍能认证响应。测试执行原版生产类，在心跳过期但 controller 仍可用的场景，观察到了修复入口被调用。
2. `restoreKilledSession()` 在前台/冷启动检查发现旧心跳时直接清除持久化连接意图。这是一次检查对会话状态的破坏性改写，不能证明隧道已经停止。原版测试观察到 `desiredConnected` 从 true 被改为 false。
3. 界面进程重新建立时，真实 controller 的实际端口、凭据与会话开始时间未统一接管。主页和 Ability 分别恢复状态，缺少同一套会话代次校验。
4. 在真实会话暂时无法确认时，启动测速内核可能停止共用的 VPN 扩展进程。新保护禁止测速预热接管尚有连接意图的真实会话。
5. 原版权威状态计算还会用进程内的 CONNECTED 覆盖已经断开的持久化意图，导致仍显示已连接。修复后保留真实存活证据供停止逻辑使用，但不会覆盖用户的断开意图。

这些是源码及边界替身测试确认的缺陷。这些测试不能认定其中哪一条就是某台手机现象的实际触发原因，也不能把短计时直接解释为系统杀进程。

## 修复后的行为

- 正常返回主页和恢复界面进程只接管已有会话，不调用连接或断开，也不重写连接开始时间。
- 旧心跳或缺失心跳出现时，先检查本机真实 controller 的认证响应；响应正常则保留原来的 TUN、Core 和计时。
- 冷启动从私有配置头读取实际端口，凭据仍从现有 AssetStore 读取。只访问 127.0.0.1，不把 headless 测速核或无认证的端口响应当作真实隧道。
- 无法确认运行状态时保留用户意图；单次前台检查不会标记连接成功、清空会话或强制重连。
- 已运行的监控必须连续 3 次同时缺少新鲜租约和 controller 认证响应，确认跨度至少 6 秒，才进入原有有限自检/修复。不是无限等待，也没有取消真实故障的修复路径。
- 监控单航班执行，积压回调不能瞬间投满负票。停止监控、切换会话、用户断开后的晚到结果不能触发修复。
- 主页通过同一编排器接管状态，移除页面自行用异步快照改写连接态的逻辑。
- 接管同一会话保留原始开始时间；接管另一个真实会话时使用那一会话保存的开始时间。

本机 controller 响应仅证明相关运行进程仍可用，不等同于节点能访问外网。真正的节点可用性仍由现有拨号/网页测试判断。网络切换、用户修改配置等原有重连路径保持其原有用途。

## 交付与真机边界

提供前台会话修复增量补丁，以及包含此前可选音频保活、30 秒后台任务自检的合并补丁。增量补丁在此前音频保活补丁之后应用；合并补丁直接应用到原版基线。不要把两份补丁重复应用。

已使用 DevEco SDK 26.0.0.105、Hvigor 6.26.8 完成 ArkTS 编译及调试 HAP 构建，包完整性与 ARM64 原生库依赖检查通过。上述 Node 测试与 SDK 编译不替代系统调度或设备验收。

编译安装后应验证：

1. 连接 5 分钟，切换应用并多次打开主页：同一会话的时长连续增长，无重新连接。
2. 锁屏 30 分钟及 2 小时后，先在浏览器访问需要代理的网站，再打开 TunBox；记录打开前后网页可用性与会话时长。
3. 区分界面进程回收、扩展进程回收与原生内核退出；确认前者不重建正常隧道，后两者仍由有限恢复处理。
4. 主动断开、从通知/卡片停止后重新打开应用，确认没有被旧探针拉回。
5. 保留 Wi-Fi/蜂窝真实切换、节点失败及配置修改的回归，避免把正常的必要重连当作本次缺陷。

本修改不涉及服务器、节点参数或原生内核；HAP 测试包不作为源码提交。
