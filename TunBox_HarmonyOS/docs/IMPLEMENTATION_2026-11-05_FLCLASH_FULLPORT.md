## 2. “智能组 UI 残余”到底是什么意思

旧报告的意思是：页面仍显示自动选择，但上一轮为了对齐 FlClash 删除了 TunBox 自己的 Smart 配置注入链，模型管理入口也被删除，造成了 UI、设置和内核配置之间的断线。**这不是 HarmonyOS 不支持 Smart，也不是 mihomo-smart 没有智能选点能力，而是移植时错误删除了本产品需要保留的能力。**

本轮恢复的是完整链路：

1. 模型存在且通过文件校验，当前订阅存在候选节点或 provider，才显示自动选择入口。
2. 点击自动选择，字段级保存 autoSelectMode=AUTO 和订阅作用域；在线时重建连接，离线时保存到下次连接。
3. RuntimeConfigBuilder 仅为用户选择的该订阅启用 Smart；其他订阅测速不继承这个偏好。
4. TunBoxProfileBuilder 在原生解析后的同一个配置 map 上追加 Smart。静态节点和 provider 都限当前 profile，排除信息节点、内部占位符和不适合作为代理的策略类型。
5. 配置声明 type: smart、uselightgbm: true、collectdata: false、prefer-asn: false、timeout: 5000；启动时确认主选择器实际选择了这个组。
6. 手动选择真实节点时回到 MANUAL，原始订阅中的分组、节点名字和独立业务组继续保留。

### 不覆盖订阅自己的同名组

订阅已经有名为“♻️ 自动选择”的 URLTest 或 Smart 时，原组保持原样，TunBox 新增组使用不冲突的名字。原 profile 文件不因此改写。新增组设为 hidden，通过单独的自动选择入口操作，避免面板重复展示。

主路由已有 Selector 时，将新增 Smart 接入它。最后 MATCH 指向叶子或不可手选策略组时，增加含 Smart 和原目标的选择器，只替换引用该目标的规则；其他业务组不被统一改成 Smart。MANUAL 模式不执行此增强。

### Smart 不一定有一个固定的“当前节点”

mihomo-smart 可按每条连接的目标和统计选出口，没有固定叶节点时 now 会返回 `Smart - Select`。这不是名字叫这个的代理节点，也不是失败。

启动校验现在识别这种动态组，并确认候选池确实存在可用类型的成员；主页显示真实 Smart 组名，具体连接出口以 /connections 的 chains 为准。App 不再用“必须有唯一叶节点”的检查拒绝 Smart，也不以旧的 App 评分逻辑覆盖内核选择。空 provider、仅 COMPATIBLE / REJECT 的候选池不能伪装成可用出口。

### 模型删除和更新

- 更新下载到临时文件，校验通过后替换，并通知页面重算入口。
- 删除前要求代理已断开，且不能正在下载，避免运行中的模型与文件状态脱节。
- 删除后退出 AUTO；重新打开设置只读状态，不会把已删模型重新铺回。
- 订阅原文若明确声明了 type: smart 且启用 LightGBM，启动仍会满足该配置的模型依赖，必要时使用内置模型。此行为与用户启用 TunBox 自动选择入口是两条来源。
- LightGBM 模型只是智能选点的一部分；节点不可达不会因为有模型而变得可达。验收使用已确认可用的节点，不把用户已确认失效的节点作为回归失败依据。

## 3. 传输层 TLS 指纹为什么不同

TLS 指纹描述 HTTPS 握手时的 ClientHello 特征，例如密码套件、扩展及顺序、支持的曲线、ALPN 等。HTTP 的 User-Agent 是握手后的请求头，**UA 相同不代表 TLS 指纹相同**。

FlClash 的订阅取回由 Dart HTTP 栈承担；TunBox 使用 Go/uTLS 经 NAPI 取回，当前使用 HelloChrome_Auto 并处理 HTTP/1.1、HTTP/2 协商。两套栈的握手特征不能称为一模一样。请求超时、状态码、Basic 认证、解压和错误传播可以对齐，但传输实现仍有差异。

这是当前 ArkTS/原生内核架构的选择，不能归结为“鸿蒙无法支持 TLS”或“鸿蒙无法使用 Dart”。要复用另一套 HTTP 栈，需要引入和维护对应运行时或原生实现。HTTP 403 还可能与凭据、IP、服务端规则等有关，不能只凭 403 就断言 TLS 指纹被拦截。

必须区分三个位置：

| 位置 | 谁发起 | 与这里 TLS 指纹的关系 |
|---|---|---|
| 获取订阅 HTTPS | TunBox 的 Go/uTLS 取回器 | 本节主要描述的差异 |
| VLESS/Trojan 等节点的 TLS/REALITY 握手 | mihomo 的协议实现 | 取决于节点配置和协议，不能拿订阅 HTTP 栈替代它 |
| 节点 URLTest 的 HTTP(S) 请求 | mihomo 经被测出站访问测试地址 | 使用真实代理出站；失败还涉及 DNS、节点、TLS、目标网站和超时 |

相关实现：bridge/fetch.go、tunbox_core_napi.cpp、CoreBridge.ets、SubscriptionFetchPolicy.ets。563 已将 proxyPort 从 ETS 经 NAPI 传入 Go；HTTPS 代理路径使用 CONNECT 后在同一 TLS 连接按 ALPN 选择 HTTP/1.1 或 HTTP/2。此传输实现仍不同于 Dart HttpClient，不能声称 TLS 指纹一致。

## 4. YAML/JSON 解析为什么不同

HarmonyOS 不限制 YAML 或 JSON。差异来自项目采用的语言库和解析职责：FlClash 的 App 层使用 Dart 数据结构/解析库；TunBox 将 YAML 解析和配置校验交给与 mihomo 配套的 Go 实现，通过原生桥返回结构化数据。

当前链路是：

1. 订阅内容进入原生 profile 校验；分享链接需要时由原生转换，校验成功再保存。
2. 原始合法 profile 按字节保存，不用 App 手写正则重组节点。YAML 锚点、别名、合并键等由原生解析器处理。
3. 构建连接配置时取原生 map，应用运行参数、DNS/规则覆盖和可选 Smart 增强。
4. 运行文件可输出 JSON。JSON 可由该 YAML 解析器接受，所以扩展名为 .yaml、内容为 JSON 并不等于配置错误。
5. 节点名、分组名、provider 归属和选择对象使用内核目录；不靠 Unicode 清洗或模糊匹配“修复”名字。

原文中的注释和锚点写法保留在 profile 文件；展开后的运行配置不承诺保留这些排版信息。要判断功能一致，应比较解析后的字段、引用和实际内核行为，不能仅比较运行文件是否还是同一种 YAML 排版。

## 5. 测速执行面是什么，为什么之前配置校验失败

“执行面”就是由哪个内核实例负责加载目标订阅并发起 URLTest。测速仍是交给 mihomo 的 /proxies/<name>/delay，不是 App 用 TCP 连接时间冒充代理延迟。

| 状态 | 执行位置 | 必须保持的约束 |
|---|---|---|
| VPN 已断开 | 无 TUN 的测速内核 | 测速不启动系统 VPN、不改变连接意图 |
| VPN 已连接，测当前已应用订阅 | 当前主内核 API | 不重启主内核，不更改用户选择 |
| VPN 已连接，测其他订阅 | 独立测速内核 | 不替换主核配置、出口或 provider 归属 |

FlClash 通常对其已经加载的主核目录测速；TunBox 还支持未连接和跨订阅测速，因此有额外的实例与生命周期编排。HarmonyOS 的 VPN 扩展、出站 socket 保护、主进程/扩展进程边界需要适配；这些不表示系统不能测速，也不表示额外编排天然正确，必须验证三个路径。

### 本次已定位的实际故障

- 运行 overlay 曾带入引用不存在 PROXY 的默认规则，叠加到名称不同的真实 profile 后，内核在 URLTest 开始前就拒绝配置。
- profile 构建与测速启动存在入口差异，容易让测速使用不匹配的规则和选择器。
- provider 节点可能只在 /providers/proxies 出现，不能只查 /proxies 就判定“无节点”；目录合并、归属和 controller 查找链需要一致。
- Smart 恢复后发现启动校验曾把正常的 Smart - Select 判为没有出口，本轮同步修正。

因此，用户看到“配置校验未通过”确实属于测速准备/执行链的问题，但不是因为 5000ms 太短，也不是 HarmonyOS 不支持。配置校验在真正拨测之前发生，调大超时无法修好悬空规则引用。

连接与测速现共用结构化配置构建链；profile 自己的规则/分组保持语义，运行覆盖只带明确的运行字段。provider 目录合并后才规划目标，中文和 emoji 名字精确传递。选择器和子策略组的出口按当前目录解析；动态 Smart 提交真实组名，由内核选点。生产策略固定并发 32、单节点 5000ms、批次守护 30000ms。

## 8. 563：全部订阅刷新失败的共同根因与修复

本节更新此前 562 的验收边界。562 曾验证测速本身，但没有覆盖「隔离测速收尾后再刷新订阅」这一跨功能顺序，因此遗漏了回归，不能以此前测速成功推导订阅刷新正常。

### 根因（真机日志与生产源码对应）

2026-11-05 17:24–17:39，多份不同订阅在 DNS 阶段报同一错误：

```text
lookup <host> on <ip>:53: dial udp <ip>:53: physical network socket bind failed: -1
```

`IsolatedLatencyCore.close()` 先停止隔离内核，再调用 `setPhysicalNetId(-1)`。旧 NAPI 实现把物理 netId 置为 -1，却仍向 `TunBoxSetSocketBinder` 注册 `BindPhysicalSocket` 回调。Go 的进程级 DNS resolver 也使用这条 socket hook，后续订阅 DNS 进入残留回调后立即返回 -1。故障发生在 HTTP 下载和 YAML/JSON 解析之前，和用户设定的 5000ms 测速超时无关，也不是 HarmonyOS 不支持订阅下载。

修复在 NAPI 的生命周期边界完成：正 netId 预检成功才注册；收尾先 `setBinder(0)` 注销，再清 netId。活跃测批绑定失败仍拒绝拨号；真实 VPN 进程仍要求自己的 protect 成功回执。未新增重试、UA 轮换或失败后绕过 VPN 保护。

## 9. 测速完成却提示“中断”：收包根因与 565 验收

### 根因与修复

564 是临时取证构建，保持旧结果语义并延后注销监听，以观察事件顺序。2026-11-05 19:03:25–19:03:28 真机日志中，3 个请求先触发 `close`（尚未收到任何字节），随后收到 154 字节的 HTTP 200 回复。旧实现把 `close` 直接当成功收尾，解析得到 code=0 后立即移除 `message` 监听，因此丢掉已经到达收包队列的成功回复；这些无结论又被 `BackgroundLatencyService` 统一解释为“测速通道已中断”。这属于客户端 TCP 收包时序错误，不是系统不能测速，也不能据此认定节点失败或用户取消。

565 的改动：

- 每个请求仍独立 TCP 连接；改为按 Content-Length 或 chunked 完整帧收尾，完整后立即主动关闭，不建复用池、不重试。请求不再要求服务端主动关闭连接；乱序 `close` 不再移除尚待交付的收包监听。
- 长度按字节统计，收全后统一 UTF-8 解码；截断、格式错误、无回复保留无结论，沿用 30s 客户端守护，内核节点超时仍固定 5000ms。
- `close()` 的异步拒绝被消费，取消与完成仍只结算一次。同步发送失败不再双重计入无结论总数。
- 新增 `wasCancelled` 区分明确取消与个别无回复；订阅卡、节点页共用完成提示，明确显示成功、真实超时、失败和未取得结果。已成功结果不会因个别缺回复整体作废，也不把缺回复伪造成超时。
