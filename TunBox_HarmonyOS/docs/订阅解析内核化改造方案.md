> 2026-10-20 方案稿。**未改任何代码**，本文是待决策的设计。
> 目标：把 TunBox 的订阅解析从「App 自研解析器」改为「mihomo 内核解析（FlClash 方式）」，
> 同时保留并增强**单链接**导入能力。

## 0. 结论先行

1. **TunBox 已经有「半个 FlClash 方式」**：`RawSubscriptionStore`（订阅原文落盘）+
   `ClashConfigGenerator.planRawProviders`（输出 `proxy-providers: {type: file}` + 组用 `use:`）
   已实现，但**默认关闭、UI 无入口、无真机验证**，且**开启即坏**（见 §2.2 的 4 个硬伤）。
2. **可行且收益确定**：把订阅解析下沉内核后，协议覆盖与字段保真由内核负责
   （mihomo 的 `NewProxiesParser` 支持 Clash YAML / base64 / **纯链接列表**，字段原样透传，
   `handleVShareLink` 负责 REALITY/fp/pcs/alpn/ed/xhttp-extra 的协议保真）。
3. **关键认知修正（重要）**：内核化**不等于**"App 放弃自研解析器"。
   内核 REST API 不返回凭据（§3.4），所以 App 侧的自研解析器**仍要留着**——
   但它的地位从「**决定能不能连上**」降级为「**决定列表显示准不准**」。
   → **"列表有、内核无"的连接级故障被根治**；仅剩"列表可能少几个节点"的显示级差异，
   且这类差异可被自动对账（内核 provider 列表 vs App 解析列表）。
4. **推荐路线**：P0 先把现有双轨修成可用（可回滚），P1 订阅默认内核化，
   P2 单链接下沉内核，P3 视产品决策决定自研链精简幅度。
5. **⚠ 2026-10-20 追加（用户报障后）**：原方案**没有覆盖**用户报的两类故障
   （「测速全部失败」/「启动代理失败」），因为测速被 §8 明确划到范围外。
   现场复盘与整改清单见 **§9**。两路独立复核后的最终账：
   - **测速侧 5 条根因**（§9.2，T1-T5，全部带源码行号），其中 T2/T5 是「误报」直接成因；

## 1. FlClash 方式到底做了什么（作为目标基线）

FlClash 不自研解析器，全部委托 vendored mihomo（`core/Clash.Meta`，FlClash 分支）：

```
Dart 下载订阅（dio，findProxy → 走代理）
  → 读 content-disposition / subscription-userinfo（流量、到期）
  → 写 profiles/<id>.yaml
  → validate(path) → 内核 config.UnmarshalRawConfig（纯 YAML unmarshal，无 ConvertsV2Ray）
  → 失败抛 MessageException，旧文件保留（原子替换）
  → profile 内的 proxy-providers：FlClash 只重写 path:（confineProviders，key='$name@$url'），
     由内核自己拉取 + 解析 provider 内容
  → 节点列表通过 IPC/RPC（getConfig / setupConfig / validateConfig / getExternalProviders）
     从内核取，不是 REST
```

要点：**下载与展示在 App，解析与凭据在内核**。

## 2. TunBox 现状体检

### 2.1 已有的部分（好消息）

| 组件 | 位置 | 作用 |
|---|---|---|
| `RawSubscriptionStore` | `commons/services/RawSubscriptionStore.ets` | 订阅原文落盘到 `cacheDir/raw_subscriptions/raw_<id>.yaml`（0700/0600） |
| `planRawProviders` | `ClashConfigGenerator.ets:1529` | 决定输出哪些 `proxy-providers` + `use:` |
| provider 输出 | `ClashConfigGenerator.ets:464-487` | `type: file` + `path: './raw_subscriptions/...'` + health-check |
| 组用 provider | `ClashConfigGenerator.ets:544-548` | `use:` 引用 provider |
| 账本 | `RawProviderStats` | missingFiles / orphaned / emitted 差额，诊断面板可见 |

### 2.2 四个硬伤（为什么它默认关闭）

**硬伤 1：开关在 UI 里没有入口。**
`useRawProviderConfig` 只存在于 `AppSettings`（`commons/models/AppSettings.ets:138`）与
`SettingsService`（:125），`pages/`、`widgets/` 里**搜不到任何引用**——用户无法开启。

**硬伤 2：与自研链叠加 → 组内同名节点。**
生成器在输出 `proxy-providers:` 的同时，**仍然**输出自研链的 `proxies:` 段
（`ClashConfigGenerator.ets:421-460` 无条件输出）。
mihomo 侧（`adapter/outboundgroup/parser.go:156-184` + `groupbase.go`）：
- `proxies:` 段的节点被包成 **CompatibleProvider** 放在 `use:` provider **之前**；
- 两者**合并进同一个组，且不去重**（`getProxies` 无 `lo.Uniq`）；
→ 同一订阅的节点在组里出现**两份同名**，且两份对象凭据可能不同（自研链那份可能缺字段）。
后果不是"报错"，而是**静默选错对象**：组按名字选中 → 命中的是自研链那份残缺节点，
这正是"列表有、内核行为不对"的经典形态。

**硬伤 3：provider 节点测速打不通。**
mihomo 的 provider 节点**不在全局 proxies 表**（`tunnel.UpdateProxies(newProxies, newProviders)`
两张表分离，`tunnel/tunnel.go:230`），因此：
- provider 节点测速必须走 `GET /providers/proxies/{provider}/{name}/healthcheck`
  （`hub/route/provider_route.go:31-35`）；
- TunBox 现有测速只有 `GET /proxies/{name}/delay`（`ClashApiService.ets:569-666`），
  且 `ClashApiService` **零 provider API** → 双轨一开，provider 节点全部 404。

**硬伤 4：无真机验证、无专项脚本。**
`docs/` 与 `README.md` 里只有开关的存在性记录，没有真机取证；
`scripts/` 下无 provider / raw 相关验证脚本。
且 `RawSubscriptionStore` 顶部注释自述"provider `path` 语义**真机无法验证**"。

**硬伤 5：provider 生命周期无设计（删除订阅 ≠ 内核节点被清除）。**
mihomo 的 file provider 在**文件消失时保留上一次成功加载的节点列表**（§3.5#2）→
删掉磁盘文件后，**旧节点仍留在内核活动表**；而 §7 风险表原先却写「删除订阅/关开关即删干净」
—— 两处自相矛盾。正确顺序（**C25**）：
先从新配置移除 provider 与组引用 → **内核成功加载新配置** → 再删磁盘文件 →
加载失败则**保留上一份可用配置与原文件**。
并必须区分「磁盘文件已删」「内核活动节点已清除」「备份/缓存已清理」三件事。

## 3. mihomo 内核侧事实基线（一手源码）

### 3.1 provider 三种类型（`adapter/provider/parser.go:ParseProxyProvider`）

| type | 语义 | TunBox 相关约束 |
|---|---|---|
| `file` | `path := C.Path.Resolve(schema.Path)` → **必须是 HomeDir 子路径**，否则 `ErrNotSafePath` **导致整份配置加载失败** | 内核 HomeDir 被设为 `cacheDir`；相对路径 `'./raw_subscriptions/x.yaml'` 解析为 `<cacheDir>/raw_subscriptions/x.yaml` → 是 HomeDir 子路径 → **通过**。前提：UI 进程与 VPN 扩展进程看到的 cacheDir 字符串一致（**需真机验证**，已有 `RAW_PROVIDER_PATH_MODE` 常量可切 absolute） |
| `http` | 内核自己拉；支持 `proxy:`（用哪个出站代理拉）、`header:`、`size-limit` | 内核拉取走**内核出站**，不是系统代理——与 FlClash 的 `findProxy` 不是一回事 |
| `inline` | `payload` 类型是 **`[]map[string]any`**（结构化 proxies 条目数组），**不是纯链接字符串** | 单链接不能直接塞进 inline |

`health-check` 支持 `enable/url/interval/timeout/lazy/expected-status`；
另有 `override`、`filter`、`exclude-filter`、`exclude-type`、`dialer-proxy`、`age-secret-key`。

### 3.2 内核解析能力（`adapter/provider/parser.go` → `NewProxiesParser`）

- Clash YAML（`proxies:` 段）✅
- 纯 `scheme://` 链接列表 ✅
- base64 链接列表 ✅
- **字段原样透传**（`override.Apply` 只改显式设置的键）→ 新协议/新字段不会丢
- 不认 sing-box JSON / Quantumult X / Surge / LOON（与主流客户端一致）

→ **这正是"自研解析器问题特别多"的根治点**：协议覆盖与字段保真由内核负责。

### 3.3 重名规则的准确边界

- `proxies:` 段**内部**重名 → **致命**：`config/config.go:907-910`
  `fmt.Errorf("proxy %s is the duplicate name", ...)` → 整份配置加载失败。
- provider 节点**不在** `config.go` 的 proxies 表注册 → 跨源同名**不触发**该致命错误，
  但会在组内产生同名成员（软冲突，谁生效取决于顺序）→ **必须主动去重**。

### 3.4 REST 数据面（决定 App 侧要补什么）

| 能力 | 路径 | TunBox 现状 |
|---|---|---|
| provider 列表 + 节点（含 `history` 延迟历史） | `GET /providers/proxies` | ❌ 无 |
| 单 provider 详情 | `GET /providers/proxies/{provider}` | ❌ 无 |
| provider 内节点测速 | `GET /providers/proxies/{provider}/{name}/healthcheck` | ❌ 无 |
| 全局表测速 | `GET /proxies/{name}/delay` | ✅ 有（但对 provider 节点无效） |
| 节点凭据（password/uuid/cipher） | **REST 不返回**（`adapter/adapter.go:136-152` 只序列化 name/type/udp/history/alive/xudp） | — |

→ **结论：内核 API 拿不到凭据。** 但这**不构成"App 必须放弃自研解析器"**——
App 本来就有订阅原文，自研链的产物本就是 App 侧的数据。
真正要变的是**自研链的职责边界**（见 §4）。

### 3.5 mihomo provider 的 9 条关键行为约束（源码级，改造必须遵守）

| # | 约束 | 出处 | 对 TunBox 的含义 |
|---|---|---|---|
| 1 | **`type: file` 忽略 `interval`，改用 fswatch 文件监听** | `component/resource/fetcher.go:212-230` | **App 改文件 → 内核即时重载**，不必重连/重启。这是"App 下载落盘 + 内核解析"路线最关键的红利 |
| 2 | **file 被删除 → provider 保留上一次成功的节点列表** | 同上 + `FileVehicle.Read` 报错只打日志 | 订阅临时拉不到时不会"节点全没"，健壮 |
| 3 | **provider 内重名 → 静默丢弃后来者，不加后缀** | `adapter/provider/provider.go:436` | Clash YAML 订阅里两个同名节点 → 后者消失且**无提示**。必须靠 `additional-prefix` 隔离 + App 侧预检 |
| 4 | **override 改名发生在去重之后** | 同上（`proxiesSet[name]` 用改名前的 name，`override.Apply` 在其后） | 两个不同原名改名后撞名 → **两个都保留**。**每个 provider 必须配唯一 `additional-prefix`/`additional-suffix`** |
| 5 | **`type: inline` 不可变**（`Update()` 只打时间戳） | `adapter/provider/provider.go:255-259` | 单链接**不能用 inline**，必须 `type: file` |
| 6 | **`payload` 可作 http/file 的备用代理** | `adapter/provider/provider.go:184-222` | 订阅挂了 provider 仍有 fallback 节点 → 天然的兜底设计 |
| 7 | **`type: http` 的 `proxy:` 走内核 tunnel**（注入 `tunnel.HandleTCPConn`，走完整规则匹配） | `component/http/http.go:70-87`、`listener/inner/tcp.go:21-42` | **内核能穿已建立的 VPN 下载订阅** —— 补上 FlClash `findProxy` 的能力。注意引导死锁（规则把订阅域名指向的组，成员又来自同一 provider） |
| 8 | **`health-check.url` 为空 → 整个 health-check 失效**（`interval` 被强制置 0） | `adapter/provider/healthcheck.go:195-217` | provider 必须显式给 `health-check.url`（TunBox 现有 `RAW_PROVIDER_HEALTH_CHECK_URL` 有值 ✅） |
| 9 | **`size-limit` 是截断不是报错** | `component/resource/vehicle.go:156-160` | 超限会得到截断 YAML → 解析报 YAML 错而非 "too large"，排查时容易误判 |

## 4. 关键产品决策（需要拍板）

**先纠正一个容易走偏的直觉**：内核 REST API 不返回凭据，**不等于** App 必须放弃自研解析器。
App 手里本来就有订阅原文，自研链的产物本就是 App 侧的数据。
真正要决定的是：**自研解析器的产物还在多大程度上参与"实际生效的配置"。**

| 功能 | 现状依赖 | 内核化后 | 说明 |
|---|---|---|---|
| 节点编辑页（`pages/NodeEditPage.ets`）改 server/port/密码 | `ProxyNode` 凭据字段 | ✅ **保留** | App 侧自研链产物不变，继续持凭据 |
| 备份导出含完整凭据（`HomePage` JSON + AES-256-GCM） | `SubscriptionService.nodes` | ✅ **保留** | 同上 |
| 节点排序 / 备注 / 分组筛选 | `ProxyNode` 元数据 | ✅ **保留** | 改为按 name 关联内核节点 |
| **实际连接用的节点** | 自研链写入 `proxies:` 段 | 🔄 **改为内核从原文解析** | ← **这才是"内核化"的本体** |
| 凭据加密落盘（`CredentialStore`/Asset） | 凭据明文不进 preferences | ⚠️ provider 原文明文文件（0600） | 安全模型略有倒退，需明示 |

**三个选项**：

- **方案甲（推荐 · 职责分离）**：自研链**继续跑**，但只负责
  ① 持有凭据（编辑/备份）② 生成 UI 元数据（归属/排序/备注）；
  **不再**参与 `proxies:` 段的生成——实际连接由内核从原文解析。
  → 连接级解析故障被根治；自研链的偏差只影响显示，可被"内核 vs App"对账自动暴露。
- **方案乙（彻底下沉）**：连自研链都删，节点列表完全来自内核 provider API。
  代价：节点编辑与含凭据备份**必须下线**（内核不给凭据），且未来新协议在 UI 上不可见。
- **方案丙（混合分流）**：标准 Clash YAML 订阅走内核；非标准格式（sing-box JSON、
  Quantumult X 等）仍走自研链兜底。复杂度居中，但 mihomo 本身也不认这些格式，
  收益有限。

> **我的建议：方案甲。** 它精准命中用户痛点（"自研解析器问题多"→ 解析错导致连不上），
> 又不牺牲 TunBox 已经做好的节点编辑/凭据加密/备份能力。
> 方案乙作为 P3 的可选终局，等 P1/P2 的对账数据证明自研链已无实际价值时再决定。

## 5. 目标架构（方案甲）

```
┌──────────────── App（控制面 · 持凭据） ────────────────────────┐
│ ① 下载订阅（UA/header/ETag/失败可见性）                          │
│      └→ 落盘原文 cacheDir/raw_subscriptions/raw_<id>.yaml         │
│ ② 自研链解析（保留！）→ ProxyNode[]（凭据 + 元数据）             │
│      └→ 凭据 → CredentialStore（Asset 加密）                     │
│      └→ 元数据索引 **稳定节点 ID** → {订阅归属, 排序权重, 备注,    │
│         原始名, 内核名, 显示名}（**四名分离**，见 C29）           │
│ ③ 单链接 → 原文追加进 links_<id>.txt（每行一个链接）              │
│ ④ 生成配置：                                                     │
│      proxies:  ← 只放"手工/非订阅"节点（单链接走 provider）      │
│      proxy-providers:                                             │
│        raw-<subId>: {type: file, path: ./raw_subscriptions/…}    │
│        link-<id>:   {type: file, path: ./raw_links/…}            │
│      proxy-groups: [{name: X, use: [raw-<subId>, link-<id>]}]     │
│                    + override.additional-prefix（命名空间，见 §3.5#4）│
└───────────────────────────┬───────────────────────────────────┘
                            │ 启动内核
                            ▼
┌──────────────── 内核（数据面 · 权威） ────────────────────────┐
│ 从原文解析（Clash YAML / base64 / 纯链接列表，字段原样透传）    │
│ fswatch 监听文件 → App 改文件即重载（§3.5#1）                   │
│ 节点列表/延迟：GET /providers/proxies                            │
│                GET /providers/proxies/{p}/{n}/healthcheck        │
└────────────────────────────────────────────────────────────────┘
```

**UI 节点列表的权威来源要换**：
- 现在：`this.subs.nodes`（App 自研链产物）——`NodeSelectionPage.ets:348`
- 改为：**内核 provider 列表**（name/type/udp/alive/history）⊕
  App 元数据索引（**按稳定节点 ID 关联**，不只靠 name）
- 内核有、App 没解析出来的节点 → 仍显示（标"未解析"），**且能正常连接**
  → 这正是内核化带来的能力增量（App 解析器不认识的协议，内核认识）
- ⚠ **浏览态回退**：内核**未运行**时节点页仍需有数据源 → 用 App 自研链结果渲染列表，
  仅禁用「测速 / 连接」（C32）。否则内核没起 = 节点页一片空白。

**节点名要拆成四个概念**（内核侧名字带 `additional-prefix`，App 侧没有）：

| 概念 | 归属 | 用途 |
|---|---|---|
| **稳定节点 ID** | App 内部 | 一切关联的主键（凭据/备注/归属/排序都挂它） |
| **原始节点名** | 订阅原文 | 用户看到的名字 |
| **内核节点名** | 内核 | 带 prefix，REST 调用用这个 |
| **显示名** | UI | 可被用户改名 |

→ 订阅改名 = 全体内核名变化，**但稳定 ID 不变** → 备注/排序/归属自动跟随（C29）。

**排序怎么办**：**排序偏好独立保存**，**不重写原始订阅文件**（C28）。
- 原始下载文件只作**恢复依据**，不承载用户排序；
- 若内核只能靠 provider 文件顺序控制列表顺序 → **另生成一份 provider 输出文件**
  （按排序后的顺序写节点），原始文件保持不动；
- 重写必须**校验 + 原子替换 + 验证内核是否成功重载**，失败恢复上一份有效文件（C27）。

### 9.3 E1「启动代理失败：yaml unmarshal errors」

#### 9.3.1 强类型字段清单（哪些段会在 yaml 层炸）

mihomo 的 `config` 包用 `go.yaml.in/yaml/v3 v3.0.5`（`config/config.go` 的 `go.mod:63`）
把整份配置 `yaml.Unmarshal` 进 `RawConfig`（`config/config.go:403-463`）。
因此 **`parse config: yaml: unmarshal errors:` 一定是"某个已知字段的类型对不上"**，
而不是 YAML 语法错（语法错会是 `yaml: line N: ...`）。

`RawConfig` 里**强类型**（会触发 unmarshal error）的字段：

| 字段 | 类型 | 风险 |
|---|---|---|
| `Port`/`SocksPort`/`RedirPort`/`TProxyPort`/`MixedPort` | `int` | 写成 `"7890"` → `cannot unmarshal !!str` |
| `AllowLan`/`IPv6`/`UnifiedDelay`/`InboundTfo`/`TCPConcurrent`/`DisableKeepAlive`… | `bool` | 写成 `yes`/`on` → **`cannot unmarshal !!str 'yes' into bool`** |
| `Mode` | `T.TunnelMode` | 值不在 `rule/global/direct` → 报错 |
| `LogLevel` | `log.LogLevel` | 值不在白名单 → 报错 |
| `FindProcessMode` | `process.FindProcessMode` | 值不在白名单 → 报错 |
| `Rule` | **`[]string`** | 任何一项不是纯字符串 → `cannot unmarshal !!seq into string` |
| `SubRules` | `map[string][]string` | 同上 |
| `DNS`/`Tun`/`NTP`/`IPTables` | 结构体 | 内部任一强类型字段错配 → 报错 |
| `Proxy`/`ProxyGroup`/`ProxyProvider`/`RuleProvider` | `[]map[string]any` / `map[string]map[string]any` | **不会**在 yaml 层报错（`any`），但会被 mihomo 自己的 mapstructure decoder 处理，报的是**另一种**错误（不是 `yaml: unmarshal errors`） |

> 关键分界：**`proxies:` / `proxy-groups:` / `proxy-providers:` / `rule-providers:` 段的
> 字段类型错配不会产生 `yaml: unmarshal errors`**（它们是 `any` + mapstructure）。
> 能在 yaml 层炸的是**顶层段**：`rules` / `dns` / `tun` / 端口 / 布尔开关。

**R3 详解**

  覆盖层 `rules`/`rule-providers`/`proxy-groups` 三段被 `extractSection` 摘走，
  **剩余原文整段**（`overrideBody`）直接追加 → 用户的 `dns:`/`hosts:`/任何带 `yes` 的段原样进内核。
- 顺带：生成器自己写的 `find-process-mode: off`（`:160`）当前无害（该字段是 string），

**R4 / R5 详解**（与另一路复核独立定位到的真根因一致）

  `rs-*` 名字** → 把自己刚生成的块也当成重复块丢掉 → 键行被丢、字段行变孤儿 → 同一个坑。

#### 9.3.7 兜底方案：生成后自检（一次性盖住 R0-R7 全部形态）

二路复核给出的关键洞察：**所有根因的共同形态是「解析→重生成」链上某处形态失真，
而 mihomo 拒载是「全有全无」**。因此最低成本的止血不是逐个堵 R0-R7，而是：

> **在配置写盘前，用与内核同源的 YAML 1.2 语义解析器解析自身产物**，
> 发现重复键/类型错 → **就地降级重建该节点/该段**，而不是把非法 YAML 交给内核。

- 这一道闸能**一次性兜住 R0/R0b/R1/R4/R5/R6 全部形态**（它们全是"某一段形态失真"）。
- 降级粒度必须是**节点级/段级**，绝不能是整份拒载 —— 否则用户还是起不来。
- 落盘位置：`ConnectionOrchestrator` 写盘后（`:712/2159/2731` 之后）。
- 长期仍应走方案甲（订阅原文直喂内核，不重生成）。

#### 9.3.8 与方案主线的关系

启动失败的**结构性**根因是：TunBox 把订阅 YAML **解析 → 重新生成**一遍，
订阅原文**从不**直接进内核。**重生成链上任何一处类型/形态失真，都会让内核拒载整份配置**，
而拒载是**全有全无**的 —— 一个节点的字段写错，整个 VPN 起不来。

这从**故障侧独立验证**了 §4 的方案甲（内核化）方向：
- FlClash 方式：订阅原文 → 内核 `config.UnmarshalRawConfig`（FlClash 侧**没有** ConvertsV2Ray
  回退，也不重生成）→ 订阅方写的原文是什么形状就按什么形状解析；
- TunBox 方式：多了一层「自己解析 + 自己重写」，每个字段都是**自己重新决定的类型**。

**代价**：方案甲是 P1/P2，**不能立即解决存量用户的启动失败**；
P0 阶段建议先落 §9.3.3 的 **R0/R4/R1/R2/R3** 修复（生成侧兜底）+ §9.3.7 的
**生成后自检闸门**，成本低、覆盖面广，且**不依赖内核化**。

### 9.10 关键取舍（需拍板的五处）

**取舍 1：C13（订阅头闪电改组测）—— 本轮降级为「可选实验项」**

- **为什么不进必做批次**：① 组测**丢失失败原因分类**（`ClashApiService.ets:752` 只保留 `delay > 0` 的成功节点，失败节点无法区分 404/503/504/超时）；② 组测是**核内无上限并发**（`groupbase.go:245` 每成员一个 goroutine），比 FlClash 的 50 更激进；③ 一旦改走组测，**T2 的触发路径即消失**（逐节点路径只剩单节点）→ C7/C8 反而变成守一条没人走的路，**掩盖**问题。
- **替代做法（保留逐节点语义 + 统一走 C7 信号量）**：更小风险，且不丢诊断能力。
- **若将来要启用**，前置条件：① 证明组测能满足订阅头闪电所需的逐节点结果语义；② 内核拨号并发可限流。

**取舍 2：C17（覆盖层顶层键）—— 这是产品语义变更，不只是修复**

- 原「白名单」方案 = 「覆盖层从此**只能加**生成器没有的段」→ 用户将**失去**用覆盖层改 `dns:`/`mode:`/`profile:` 的能力。
- 本轮改为**合并策略**：生成器拥有的键（禁止覆盖 / 允许覆盖二选一）+ 用户可配置的键走**结构化合并**（不再拼接两段原始 YAML）+ 未知键**明确报错**（不静默删除）+ 合并后再校验重复键与类型。
- **仍需产品拍板**：生成器拥有的键（`dns`/`mode`/`profile`/`mixed-port`/`log-level`/`ipv6`/`sniffer`/`hosts`）到底是**禁止覆盖**还是**允许覆盖并结构化合并**。
- **建议**：允许覆盖 + 结构化合并（用户能力不丢），代价是合并逻辑必须写规格。

**取舍 3：证据强度与 R0 表述**

- 那 66 份配置是**真实生成器产物**（✅），但**拒载判定来自自写 yaml.v3 仿真器**（⚠），**行号未在真机内核复现**。
- 因此 R0 表述从「**最高频**」降级为「**当前语料中已发现且影响范围较大**」。
- **实施前应把这批样例逐一变成真实内核加载回归测试**，不把仿真结果直接当最终结论。
- 采集到真实用户订阅的命中率统计后，再决定优先级是否调整。

**取舍 4：并发数 50 的最终口径**

- FlClash 的 50 = **内核同时拨号数**（`mBatch`，IPC 通道）；TunBox 的 50 = **并发 worker 数**（客户端 REST 通道）。
- REST 下墙钟由**连接池容量**决定（`⌈N/8⌉×5s`）→ 客户端并发 8/50/100 墙钟几乎相同。
- 正确落地：`LATENCY_CONCURRENCY = 50`（worker 数）+ `LATENCY_INFLIGHT = 8`（在途请求数）。
- **「真·并发 50 拨号」只有 IPC 能实现**（需重编 49MB `libgojni.so`，本机缺 OHOS Go 工具链，暂不可行）。
- **最坏墙钟对账**：`⌈50/8⌉×5s ≈ 35s` < `BATCH_DEADLINE_MS = 90000`（90s）→
  **deadline 不会砍掉排队尾部的节点**（`LatencyEngine.ets:379-381` worker 各自检查 deadline，旧实现共用 deadline 的问题已修）。

**取舍 5：HTTPS 的边界**

- 目标是**默认值与历史默认值升级为 HTTPS**，**不是**把所有用户自定义 HTTP 地址强行改写。
- 保留用户可配 URL 与 http 回退（个别出口掐 gstatic 的 TLS SNI 有真机实证 `a3fe45d`）。
- `AppSettings.ets:350-352` 应从「强制 https→http 降级」改为**历史 http 单向升级**。

### 10.1 结论更正（三条；第 ① 条推翻了本方案的一处推演）

**① R3「布尔字面量」口径 —— 原表述不成立，已按内核实测更正。**

原方案 §9.3 R3 写的是「yaml 1.1 的 `yes/no/on/off` 解析为 `!!str`，落进 bool 字段 →
`cannot unmarshal !!str into bool` → 整份拒载」。本轮用**真实内核**（Mihomo Meta 1.10.0，
`mihomo.exe -t` 逐写法验证）实测，结论**正好相反**：

| 写法 | 真实内核 | 说明 |
|---|---|---|
| `allow-lan: yes` / `YES` / `on` / `ON`（**裸写**） | **通过** | yaml.v3 对 **bool 目标**有 YAML 1.1 兼容分支 |
| `allow-lan: "yes"` / `"on"` / `"no"` / `"OFF"`（带引号、兼容表内） | **通过** | 同上 |
| `allow-lan: true` / `false` / `TRUE`（裸写） | **通过** | |
| `allow-lan: "true"` / `"True"` / `"TRUE"` / `"false"` / `"1"` / `"0"` | **整份拒载** | `cannot unmarshal !!str \`true\` into bool` |
| `allow-lan: 1` / `0` / `2`（**裸写数字**） | **整份拒载** | `cannot unmarshal !!int \`1\` into bool` |

原因：yaml.v3 的 resolve 表只认 true/false 六种写法（这是 YAML 1.2 core schema 的一般结论），
但 **decode 层对 bool 目标另有一层 YAML 1.1 兼容分支**，会把
`y/Y/yes/Yes/YES/on/On/ON` → true、`n/N/no/No/NO/off/Off/OFF` → false；
该兼容表里**没有** `true/True/TRUE/false/False/FALSE/1/0`。

**处置口径（代码与门禁均已按此实现）**：
致命集合 = **带引号的 `true/false/1/0`** + **裸写的 `1/0`**；
- 裸写 `yes/no/on/off` → 内核吃得下 → **不拦、不改**用户文本（改写仅为规范化，语义相同）；
- 带引号的 `"yes"/"on"/"no"/"off"` → 内核吃得下 → **保持原样**；
- 裸写 `1/0` → 归一为 `true/false`；裸写其它数字（如 `allow-lan: 2`）意图无法判定 →
  **不猜**，判为阻塞（拦下写盘、保留上一份可用配置）。

**② 「mihomo 对重复顶层键是后者覆盖前者」是错的 —— 实际是报错、整份拒载。**
yaml.v3 的 `uniqueKeys` 默认开启，重复键进 `TypeError`，错误文本
`yaml: unmarshal errors:\n  line N: mapping key "xxx" already defined at line M`
—— 正是用户报障的 `parse config:yaml: unmarshal errors:` 原文形态。
R2 / R4 / R5 三条根因的认知根源即在此；代码里两处错误注释已改正（见 C16/C17 说明）。

**③ 本机有真实内核可用 —— §9.3.3「行号来自自写仿真器、未在真机内核复现」的局限已被解除。**
本机内核二进制：`C:\Worker\TunBox\mihomo-build\mihomo-smart-<hash>\mihomo.exe`
（Mihomo Meta 1.10.0，go1.24.7，与 App 内置的是同一份构建）。
`mihomo.exe -t -d <home> -f <cfg>` 即真判决。本轮已用它把 R0–R6 的形态逐条复现，
并固化为可重复执行的门禁脚本（§10.3）。

### 10.5 已知缺口与风险（诚实声明）

1. **数值字段的非法值不在写盘闸门覆盖范围**：如节点 `port: on` / `port: 8389x`
   → 由 mihomo 自己的 proxy 解析器报错（`cannot parse 'port' as int`）→ 整份拒载。
   本轮闸门**不覆盖**这一类（要覆盖需逐协议的字段类型表）。
   处置：**生成侧对节点字段做类型化产出**（端口/密码一律用数值/字符串形态），
   写盘闸门只负责 yaml 层形态。该缺口已由 `verify-config-validator-kernel.mjs` 第 7 段**如实断言**（证明这类确实会炸 + 明确记录未覆盖）。
2. **覆盖层 `dns:` 是「整段替换」而非字段级合并**：用户只写一行 `dns: enable: false`
   就会顶掉生成器的整段默认 DNS（fake-ip / DoT / 防泄漏 DNS）。这是 §9.10 取舍 2 的直接后果。
3. **C14（anytls）当前不命中**：HEAD 已把 anytls 放进结构化白名单 → 本条是防回归兜底。
   若真机仍在丢 anytls，需另查生成端 / 订阅源侧（**不在本轮结论内**）。
4. **双轨 provider 的节点名撞名**（C24 残留缺口）：provider 原文里的节点名由内核自己解析、
   不经生成器的改名逻辑 → 可能与 `proxies:` 段同名（内核报 `proxy X is the duplicate name`）。
   根治要在 provider 落盘时给节点名加前缀（属组 C）。
5. **本轮所有结论都是离线结论**：真实内核已接入，但**真机**（连接池、TLS、进程行为）未验证。
6. **闸门不是完整 YAML 解析器**：不做锚点/别名（`&`/`*`）、多文档（`---`）、块标量（`|`/`>`）
   的完整语义解析 → 「校验通过」不等于「内核一定能加载」。

### 11.7 大订阅（几百节点）「测几个就不测了」—— 四处算术/阈值问题（2026-10-22）

真机导入 600 节点订阅后：`latency batch start nodes=547 ... timeout=5000ms` →
26 秒后 `latency channel recovery failed` → `latency batch aborted: streak=9 measured=2` →
`done ... measured=2 timeout=543 unavailable=true`。四个独立成因，全部按「不猜、可回退」修：

| # | 问题 | 修法 |
|---|---|---|
| 1 | 整批硬截止**固定 90s**。547 节点 / 在途 32 ≈ 18 波 × 5s ≈ 90s+ ⇒ 队尾全被截成「未测」 | `LatencyEngine.deadlineForBatch(n)`：按波数估算 + 20s 余量，下限 90s、上限 15min |
| 2 | 作废阈值固定 6 连击。32 路在途把 `/version` 探针压到超时 → 误判「通道不可用」→ 整批中止 | `abortStreakFor(n)`：`max(6, ceil(n/64))`，小订阅灵敏度不变 |
| 3 | 组测外层超时恒为 `timeoutMs + 5s` = 10s，而核内 600 节点要 ≈ 60s ⇒ 客户端自己掐断并归类成「通道不可用」 | `testGroupDetailedResult(..., expectedNodes)`：按 `ceil(n/50)` 波数加预算，上限 5min |
| 4 | 大订阅仍走逐节点 REST（客户端 HTTP 栈是同 host 连接池，扛不住） | `nodes >= 120` 走**内核组测**（`BackgroundLatencyService.runKernelGroupTest`，一次调用、核内 `mBatch=50`），与三家的做法一致 |

真机复验（643 节点、未连接走无头测速核）：
`kernel group test done: total=643 measured=26 timeout=617 notInCore=0`，界面同时出现
`313ms` 与「超时」两种读数 —— **测完整批、不再中途停**。26/643 是这批免费订阅的真实存活率。

> 仍未做：大订阅的「逐节点独立 RTT」口径（内核组测只回成功的延迟，失败无法细分原因，
> 目前用「在内核代理表里 → 真超时 / 不在 → 未生效」两分法兜住）。
