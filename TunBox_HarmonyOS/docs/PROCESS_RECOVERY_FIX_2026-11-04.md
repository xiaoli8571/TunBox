# 启动诊断与异常退出恢复（2026-11-04）

## 本次需求

保留真正的启动失败原因，减少“心跳缺失或过期”覆盖所有问题的误报；代理进程异常退出后自动恢复。手动断开、系统严重内存压力主动止损、配置/授权错误以及恢复预算耗尽后必须停止，不能形成重启循环。

## 已确认的问题

- `probeCore()` 原来只看 15 秒心跳租约，即使认证 `/version` 能返回成功仍判内核死亡。租约实际由扩展 ArkTS 每 5 秒刷新，不能等同于 native 内核的生死。
- 启动失败后的健康检查用第一个下游失败覆盖 `lastError`，配置、授权、启动超时等原始错误因此消失。
- `restoreKilledSession()` 对已失联的持久会话只返回 `runtime-unconfirmed`，不会启动恢复。进程重建后也没有监控接手这条会话。
- 恢复尝试的失败回滚会调用 `clearSessionIntent()`，把异常退出改写成用户已断开，退避管理器随后无法继续重试。
- 快捷宿主另有一套 `VpnQuickStart('start')` 恢复和定时重试，与编排器预算和取消代次不共用。
- 冷 UI 接管活隧道直接从 DISCONNECTED 写 CONNECTED，真实状态机拒绝此迁移；旧运行时沙箱用宽松替身，未覆盖这个问题。

## 修改

- 心跳过期后用认证控制接口复核；同一轮核心/API 探针共用一次认证请求。没有连接意图时跳过核心和接口检查。
- 自检报告保留在诊断中，首个启动错误继续供 UI 显示。每个自检 await 后核对连接代次，过期结果不能覆盖用户的新操作。
- 已间隔确认失联后直接进入统一退避恢复，不再等待依赖已退出内核的 DNS/出口自检。关闭健康检查也不关闭异常退出恢复。
- 冷启动、前台和快捷宿主共用恢复单航班；先接管仍活着的隧道，再恢复未结束的连接意图。接管走合法 RECOVERING → CONNECTED 迁移，不刷新原连接时刻。
- 每次恢复前重读持久意图、会话代次并复核控制接口；若进程已经自行恢复，就接管而不重启。只有异常恢复的回滚保留意图，手动断开照常清除。
- 最多 3 次，退避 1/2/4 秒；配置错误、分流参数、VPN 授权/其他 VPN 冲突立即停止。耗尽后写 failed，相同失败会话不会因回前台无限复活。
- 物理断网暂停恢复，恢复联网再继续；取消尚未执行的断网预约不消耗恢复次数。
- 在 AbilityStage 启用系统 `appRecovery`，UIAbility 声明 recoverable 并同意故障状态保存。重启目标固定为 EntryAbility，故障恢复时不重放快捷方式的 toggle。
- 真机还发现系统会先重建主进程而不创建 UIAbility。新增 `StageSessionRecovery`：只在本应用主进程、且 UI 尚未接管时读取持久会话并恢复；VPN/Form/Work 进程不执行，UI 启动优先。进程身份使用 API 11+ 无需权限的本应用进程查询。
- 冷 UI 接管也必须认证控制接口；恢复时单独准备端点，不再对已经失联的 mixed-port 白等 4 秒。退避完成前必须同时确认实际 API 响应，不能凭退出后残留的新鲜心跳宣布恢复成功。
- 超时只报告实际观测，不再承诺“下载已补齐，再点即可正常启动”。

## 平台边界

两个进程都已被 SIGKILL 或整应用被用户强行停止时，应用里的定时器无法执行。当前实现不引入受限权限、常驻原生子进程或高频 WorkScheduler 来绕过系统管控。

`appRecovery` 适用于系统支持的故障场景，不等于任意 SIGKILL 自动拉起。官方说明连续两次系统故障重启必须间隔超过一分钟。低内存回收、用户强停、JS 崩溃、冻屏必须分别验收，不能把启动应用后恢复当作全应用被杀后静默自启动。

依据：[OpenHarmony 应用故障恢复指南](https://raw.githubusercontent.com/openharmony/docs/master/en/application-dev/dfx/apprecovery-guidelines.md)、本机 SDK `@ohos.app.ability.appRecovery.d.ts`。新 SDK 的 CPP_CRASH 恢复能力还取决于设备 API 版本，本轮不将其作为已验证能力。

## 验证

- `node scripts/verify-process-recovery-runtime.mjs`：23 个生产代码运行时用例通过。包括 API 存活但心跳过期、原始错误、冷恢复合并、退避期间接口恢复、用户/另一 Ability 停止、自动回滚、过期回滚、三次耗尽、断网暂停、关闭健康检查、不可重试错误、迟到自检、残留心跳和无 UI 主进程恢复。
- 编排器运行时沙箱改用真实 `ConnState`、`ConnectionStateMachine`、`ReconnectManager`、健康探针及错误策略，保留 OS 边界替身。

本轮恢复实现通过 clean release 构建和资源编号、构建配置、签名身份门禁。最终与出口 IP 修复一同交付，包和 SHA256 见 [出口 IP 链路记录](PUBLIC_IP_ROUTE_FIX_2026-11-04.md)。临时进程终止和 JS 故障测试入口未进入最终包，已对最终 HAP 的 abc 字节码检查对应标记均不存在。

### 真机中间证据

设备 MLR-AL00 / `192.168.10.8:39933`，当前订阅和节点保持用户设备上的吹雪云 / 美国·移联01。

外部 HDC shell 不能 SIGKILL 发行版进程（Operation not permitted），也不能 stop 未导出的 VPN Ability。为验证真实异常退出，使用一次性的本地签名测试包，从目标进程自身调用 `ProcessManager.kill(9, process.pid)`；测试入口在构建后立即还原源码，不进入交付包。

- 后台 VPN SIGKILL：11:15:17.797，PID 11706 自身发信号 9。系统 PROCESS_KILL 记录明确 `FOREGROUND=0`。
- 无手动打开应用；11:15:32.857 / 35.905 两次负票，39.069 第三次确认，40.084 自动恢复首轮，42.427 恢复原节点，耗时 24.630 秒，新 VPN PID 11992。
- 前台 JS 故障：11:12:51 左右触发后 UI PID 9957 → 10447，系统自动重建；原节点随后恢复。这个中间包仍有残留心跳误判，已据此增加认证复核，最终包另行验收。
- UI SIGKILL：9009 于 11:11:33 左右退出后，系统 11:11:34.085 已运行新主进程 9957 的 AbilityStage，但直到手动打开的 11:11:54.205 才创建 EntryAbility。这就是新增 StageSessionRecovery 的实机依据，不能把进程已重建当成 UI 恢复入口已经运行。
- 补齐 Stage 后再次在后台 SIGKILL 主进程 14427（11:19:14.670 预约，5 秒后发送信号）。无手动打开应用，新主进程 14968 的 Stage 于 25.652 排程恢复，34.456 已连回原节点，新 VPN PID 14999，约 15 秒恢复。新主进程期间没有 EntryAbility.onCreate，证明恢复由 Stage 入口完成；这个结果依赖系统先重建主进程，不能推广为所有设备强停都能拉起。
